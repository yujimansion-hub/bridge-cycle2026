## 必須の確認事項（正式募集前）
1. 許可証名の定義：保健所発行の「営業許可証」自体が同一書類の可能性あり。別途求めるのが食品衛生責任者資格証、届出受理、車両営業許可などか主催者と所管保健所で確定する。
2. 書類の取扱責任者、保存目的、保存先、閲覧権限、保存期間と削除方法を規定。プライバシーポリシーへ明記する。
3. 出店料の収納主体（主催者かBRIDGE CYCLEか）、キャンセル・返金条件、税込料金、請求書・領収書の発行者を正式合意。
4. 認可済み枠データ、枠の重複防止、決済期限、未入金時の解放ルールを実装。

## 安全なアップロードAPIの契約（実装するバックエンド側）
- 許可されたHTTPSの `POST` multipart/form-dataエンドポイントのみ使用。
- CORS許可元は `https://www.bridgecycleco.com` に限定。アップロードのレート制限・自動投稿対策必須。
- フィールド：`applicant`, `email`, `health_document`, `same_document`, `business_license`（同じ場合は省略）, `preferred_dates`, `business_type`, `products`, `consent`。
- 両画像は最大10MB、jpeg/png/webp/heic/heifを想定。**サーバー側**でファイルシグネチャとサイズ、危険なメタデータを検査し、必要に応じてマルウェアスキャン。クライアントのMIMEは信用しない。
- 非公開ストレージに暗号化保存し、保存キーを推測できないものにする。一般公開URLやGitHub、ローカルストレージに保存しない。操作ログに氏名・画像・ファイル内容を記録しない。
- 正常受付でのみHTTP 200/201および `{"status":"pending_review","application_id":"..."}` を返却。審査完了を意味しない。失敗時は適切なエラー。
- 申込者への受領通知、管理者の審査結果通知を設計。口座やカード番号をサイトのフォームで直接受け取らない。

## 決済・枠管理（バックエンドの次フェーズ）
- 状態：`lead → uploaded → under_review → approved_payment_pending → paid_confirmed`。不備時は `needs_resubmission`、辞退時は `cancelled`。
- **審査通過＋確定枠**の状態のみ、収納主体のStripe Checkout等で出店日別の個別決済を生成してメールで案内する。
- 一定期限まで枠を仮押さえし、期限切れは解放。満枠時は決済ページを発行しない。
- 支払いの最終確認は**署名検証済みWebhook**で行い、サイトの決済完了画面だけで確定処理しない。Webhook重複に備え冪等化。
- 振込の場合は入金照合後に運営管理者が確定。領収書、キャンセル・返金処理を明文化。

## 接続の手順
1. 非公開画像ストレージと書類審査用バックエンドを構築して検証する。
2. 事前にテスト画像で安全性・容量超過・許可形式・二重申込・端末別動作を検証する。
3. `minakusa-ekimae.html` のメタタグ `bc-secure-upload-endpoint` の `content` を、**本番HTTPS API URL**に変更する。未設定のままでは送信できない。
4. 決済アカウント・Webhook・領収書・返金を確認して正式募集を開始する。
5. `noindex` は正式公開するまで維持し、主催者と条件確定後に切り替える。
